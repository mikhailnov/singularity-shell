# Печать плана дня

## Проблема

В официальном десктопном клиенте SingularityApp (Electron) при нажатии
Ctrl+P или выборе «Файл → Напечатать план дня» формируется красиво
отформатированный документ с планом задач на сегодня. В нашей оболочке на
QtWebEngine та же операция даёт пустой лист.

## Почему не получается

### Как устроена печать в оригинальном приложении

1. **CSS-правило `@media print`.** В CSS приложения есть два правила:

   ```css
   @media print {
     @page { size: a4 landscape; margin: 1cm; }
   }
   @media print {
     body * { visibility: hidden; }
     .popup-day-tasks, .popup-day-tasks * { visibility: visible; }
   }
   ```

   При печати скрывается **вообще всё**, кроме элементов с классом
   `.popup-day-tasks`. Именно этот блок содержит красиво отформатированный
   план дня.

2. **Блок `.popup-day-tasks` создаётся главным процессом Electron.**
   В JS-коде вендора есть функция-обработчик `printToday`, которая:
   - собирает задачи на сегодня,
   - сохраняет их в IndexedDB через `db.updateByInstructions({printTodayTasks: […]})`,
   - вызывает `window.print()`.

   Однако сам элемент `.popup-day-tasks` в DOM **не создаётся** кодом
   рендерера — он создаётся главным процессом Electron (файл
   `build/main/index.js`), который открывает отдельное скрытое окно
   `BrowserWindow`, загружает в него специальную вёрстку и вызывает
   `webContents.print()` уже в этом окне.

3. **В веб-версии** (обычный Chromium) при нажатии Ctrl+P открывается
   стандартный диалог печати браузера, и в **превью отображается
   именно план дня** (отформатированный, а не скриншот страницы).
   Это означает, что где-то в процессе рендеринга для печати браузер
   всё-таки создаёт элемент `.popup-day-tasks` и применяет к нему
   вендорские `@media print`-правила. Однако через CDP (`Page.printToPDF`)
   этот механизм не воспроизводится — вероятно, реальный диалог печати
   Chromium запускает полноценный проход рендеринга с участием Service
   Worker, который и создаёт нужную структуру DOM.

### Что мы попробовали

1. **`window.print()` через C++ (`QWebEnginePage::printRequested`).**
   Перехватываем сигнал, показываем Qt-диалог печати
   (`QPrintDialog`), вызываем `QWebEngineView::print()`.
   **Результат:** пустой лист — срабатывает `@media print { body * {
   visibility: hidden } }`.

2. **`view->printToPdf()` с тем же сигналом.**
   Сохраняем PDF и открываем в системном просмотрщике.
   **Результат:** пустой PDF (894 байта, только заголовок) — та же причина.

3. **Инжекция CSS-правила, отменяющего скрытие.**
   `@media print { body * { visibility: visible !important; } }`
   **Результат:** печатается скриншот текущей страницы (боковая панель,
   заголовок, список задач) — не отформатированный план.

4. **Попытка скрыть UI-элементы (`display: none` на сайдбар и хедер).**
   **Результат:** пустые места на месте скрытых элементов, полезная
   область обрезана — CSS-раскладка страницы (flexbox/grid) не
   перестраивается под печать.

5. **Отдельное окно печати.**
   Создавался новый `QWebEngineView`, загружался тот же URL,
   инжектировался агрессивный CSS (`position: static`, скрытие
   сайдбара/хедера, содержимое на всю ширину). Затем `printToPdf`
   на этом окне.
   **Результат:** ошибки JS (нет `preloadApi`), даже после добавления
   PreloadBridge — пустой или обрезанный вывод.

6. **Отправка Ctrl+P как клавиатурного события в JS.**
   `document.dispatchEvent(new KeyboardEvent(…))` — чтобы вендорский
   обработчик сам запустил процесс печати.
   **Результат:** ничего не произошло — обработчик не среагировал на
   синтетическое событие.

7. **Эмуляция `beforeprint`/`afterprint`.**
   Проверено в реальном Chromium через CDP — вендор не вешает
   обработчиков на эти события, попап `.popup-day-tasks` не появляется.

### Вывод

В реальном Chromium печать плана дня **работает** — в диалоге печати
отображается отформатированный план. Механизм, с помощью которого браузер
создаёт попап `.popup-day-tasks` при подготовке страницы к печати, не
удалось воспроизвести ни через `QWebEnginePage::printToPdf`, ни через
CDP `Page.printToPDF`.

Вероятные причины:
- Реальный диалог печати Chromium запускает полноценный проход
  композитинга с участием Service Worker, который и создаёт нужную
  структуру DOM;
- Либо рендеринг для печати в Chromium использует отдельный поток
  композитинга, в котором вендорский JS успевает отработать и создать
  попап до того, как применяются `@media print`-правила.

QtWebEngine не предоставляет доступа к этому механизму — ни через
`printToPdf`, ни через `QWebEngineView::print`. Требуется дальнейшее
исследование с использованием отладчика Chromium и трассировкой
событий Service Worker при печати.
